# Resource framework end-to-end checkpoints

**All five Offering CRUD operations are verified over real HTTP on app-local memory and PostgreSQL.** Viewers can read a single offering or page through their organization’s offerings with a type filter and ordered sort keys. Both the rows and the total count are scoped to the selected tenant. Editors can create and update offerings, and administrators can delete them. The PostgreSQL tests write through one server and read through a second server with an independent pool. [List acceptance scenario](../../packages/apps/tests/e2e/offeringList.fixture.ts) · [PostgreSQL tests](../../packages/apps/tests/e2e/postgresOfferingHttp.test.ts)

This is an implementation sequence within the [resource framework plan](resource-framework.md#program-order). Phase 1 supplies the contract and client. The planned Phase 1.5 form will exercise the same contract with an injected fetch. Phase 2 supplies the listening app and test kit. Phase 3 repeats the caller-facing suite against PostgreSQL. The first HTTP test is a checkpoint within Phase 2.

**2026-11-19 handoff.** All 12 checkpoints below are complete. Get is the first reusable ORM handler. The next proposed checkpoint is Delete, using the existing HTTP scenarios for role checks, tenant isolation, repeated deletion and concurrent deletion. [Weekly handoff and verification](resource-framework.md#weekly-handoff) · [Delete acceptance test](../../packages/apps/tests/e2e/offeringDelete.fixture.ts)

## What exists today

| Area | Implementation | Verified boundary |
| --- | --- | --- |
| Resource and contract | The [resource system](../../packages/apps/src/model/createResourceSystem.ts) records each declared endpoint. The [generated contracts](../../packages/apps/src/endpoints/createEndpoints.ts) derive the requests and success envelopes. Get, Update and Delete map the primary key to the item URL. Update places supplied write fields in the PATCH body. List carries paging, declared equality filters and ordered sort fields in the collection URL and projects each returned row. | The HTTP adapter uses the same schemas and matches the route handler to the original endpoint object. |
| Client | The [typed client](../../packages/apps/src/client/createClient.ts) owns the instance's tenant header and bearer token. | A [real-socket test](../../packages/apps/tests/e2e/createOfferingHttp.test.ts) inspects HTTP status and JSON before the client decodes the response. |
| Server | The [API factory](../../packages/apps/src/express/createApi.ts) resolves route classes and compiles the [HTTP pipeline](../../packages/apps/src/express/pipeline.ts) on the shared [foundation chain](../../packages/foundation/src/chain/binding.ts). | The [compiled example](../../packages/apps/tests/e2e/emittedOffering.test.ts) starts in native Node and discovers its sibling routes. |
| Test kit | The [test kit](../../packages/apps/src/testing/index.ts) uses the same API factory, with its own opaque tokens, memberships and ephemeral loopback listener. | An existing token sees a role change on its next call. A signed-in user without a membership in the selected organization receives 404. |
| Database | The [ORM adapter](../../packages/apps/src/mikro-orm/index.ts) derives the entity from the resource. Its unit of work binds the verified tenant to a fresh manager, and the database routes use the reusable Get handler. | Through a second PostgreSQL pool, tenant A reads its committed offering and tenant B gets the same 404 as for a missing ID. |

## Keep the application and the tests small

Declare `Offering` once under `packages/apps/examples/crud-api/common/src/resources/`. The common app selects its tenant resource and ordered roles. The resource declares its fields, enables the operations it serves and supplies its access map. The in-memory routes bind all five operations to the app’s store. The PostgreSQL routes opt into the ORM’s Get default and supply the other four handlers. The test supplies an actor, a tenant and the flat input. Derive paths, header names, operation keys, schemas, response codes and field grants from the contract. Put each repeated concern in its owning layer. [Foundational principles](../ARCHITECTURE_AND_PHILOSOPHY.md) · [Target Offering declaration](resource-framework.md#one-resource-end-to-end-target-call-sites)

The browser-safe apps root owns the model, endpoint and client. The Node-only `/express` entry owns request dispatch and routing, `/runtime` owns lifecycle, and `/testing` owns isolated test identities and setup. Factories take named options, derive defaults, and let the caller override dependencies. Each test app owns its listener, client credentials and memberships. The default routes keep an in-memory store per app. The database-backed routes use the host’s ORM pool and the entity’s tenant filter. [Layer ownership](resource-framework.md#layers-and-owners)

The target happy-path call in Vitest looks like this. The example supplies a valid offering type, user and organization. The framework owns token issuance for that test identity, route lookup, HTTP transport and response decoding.

```ts
const app = await createTestApp({ resources, routes: [OfferingRoutes], env: { APP_ENV: 'test' } });
try {
  const editor = app.as({ user: alice, tenant: organizationA, role: 'EDITOR' });
  const result = await editor.call(CreateOffering, { name: 'Starter', description: 'Trial plan', type });
  expect(result.code).toBe(201);
  if (result.code === 201) {
    expect(result.data.links).toEqual([]);
    expect(result.data.createdAt).toBeInstanceOf(Date);
  }
} finally {
  await app.close();
}
```

## Implementation order and acceptance

1. **Derive a real Create contract (complete).** The example declares editable `name`, create-only `type`, defaulted `links`, readable timestamps, a tenant field and unmarked `vectorStoreId`. The caller may omit `links`, the decoded handler input gets `[]`, and supplied `id` or `organizationId` fails validation. The fixture typechecks the handler against the exported endpoint and checks that an incomplete handler result is incompatible. [Resource system and contracts](resource-framework.md#phase-1--core-model-and-contracts-browser-safe)
2. **Drive the contract through the client (complete for injected fetch).** The public test checks the URL, headers, JSON body, 201 response projection, date round trip, typed 422 and a rejected fetch. The [client tests](../../packages/apps/tests/client/createClient.test.ts) also exercise independent tenant headers. Phase 1.5 will use this same client in a form and map a server issue on `name` to the field. [Client contract](resource-framework.md#19-client-appssrcclient) · [Thin UI spike](resource-framework.md#phase-15--thin-ui-spike)
3. **Bind and serve the routes (complete for all five Offering operations).** Foundation owns the chain shared by the CLI and HTTP. Each app instantiates its selected route classes, matches handlers against its resource-system inventory and rejects absent or duplicate handlers before listening. Discovery and explicit classes are both tested. [Shared chain](resource-framework.md#03-the-typed-middleware-chain-built-in-phase-2) · [Routes tests](../../packages/apps/tests/express/routes.test.ts)
4. **Compile the HTTP pipeline (complete for all five tenant-owned Offering operations with user and role rules).** The server enforces a byte limit, verifies the bearer token, looks up membership and checks the role floor before decoding the body. It validates field-level write roles, calls the handler and encodes one projected response. Unsupported ownership and access declarations fail at startup. API keys, conditional access rules and custom middleware groups remain later Phase 2 work. [Request pipeline](resource-framework.md#24-request-pipeline-per-route-compiled-once-at-startup) · [Pipeline tests](../../packages/apps/tests/express/pipeline.test.ts)
5. **Start the same app from Vitest (complete for this checkpoint).** The test kit calls `createApi`, binds loopback port zero and builds the client from the actual address. Each app resolves its own opaque tokens and tenant memberships. Unset or non-test `APP_ENV` rejects the test verifier. The listener drains active requests and forces closure at the deadline. General runtime service discovery and lifecycle are still planned. [Test kit](resource-framework.md#211-test-kit-epsilon-asiappstesting) · [Listener](../../packages/apps/src/runtime/httpListener.ts)
6. **Add the tenant-isolation read (complete for the in-memory app).** `viewer.call(GetOffering, { id })` sends `GET /offerings/:offeringId`. Both viewers use the same read role. Each can read its own organization's row. B’s reads of A’s ID and a missing ID have identical public HTTP 404 envelopes except for trace IDs. A second app serving A starts with an empty store. The PostgreSQL checkpoint below runs the same caller-facing assertions. [Real HTTP tests](../../packages/apps/tests/e2e/getOfferingHttp.test.ts) · [Database tests](resource-framework.md#38-tests)
7. **Persist Create and Get in PostgreSQL (complete).** Two HTTP apps use the same schema through independent pools. An editor creates on the first app and a viewer reads the committed result on the second. The test checks raw HTTP envelopes, typed dates, tenant ownership, equivalent foreign/missing 404s, and a server-only value present in storage. [PostgreSQL acceptance test](../../packages/apps/tests/e2e/postgresOfferingHttp.test.ts) · [Plan §3.1](resource-framework.md#31-entities-from-the-same-class)
8. **Update a stored offering (complete).** The generated endpoint accepts a required primary key and optional update-writable fields. The same test patches a single field, replaces links, sends an empty patch, and checks row visibility after denied and invalid writes. A PostgreSQL test reads through a second pool and verifies the persisted server-only value and two concurrent edits. 9. **Delete a stored offering (complete).** An administrator sends a bodyless Delete and receives HTTP 200 with an empty success envelope. ## What the HTTP tests must observe

The [example entry](../../packages/apps/examples/crud-api/api/src/main.ts) loads the common contract independently of route discovery. Omitting the route class produces a startup error naming `CreateOffering`. The tests supply `APP_ENV=test` explicitly. The cases below run over HTTP, alongside missing-tenant (400), wrong-tenant (404) and insufficient-role (403) cases.

| Case | Arrange and send | Required evidence |
| --- | --- | --- |
| Create succeeds | An editor in tenant A calls `client.call(CreateOffering, …)` with `name`, `description` and `type`. The handler returns a row with a known timestamp and a populated `vectorStoreId`. | Handler runs once with A’s organization and defaulted links. Raw HTTP status and JSON `code` are 201. The raw JSON omits `vectorStoreId` and contains the ISO timestamp. The typed caller receives the same instant as a `Date`. |
| Validation reaches the server | The authenticated editor sends syntactically valid JSON with an empty `name`. | HTTP and envelope report 422. A nonempty trace ID and an issue with flat path `name` reach the caller. Handler runs zero times. |
| Authentication precedes validation | Repeat the exact body and tenant header with the bearer token omitted. | HTTP and envelope report 401 with `Auth.UNAUTHENTICATED` and a trace ID. Handler runs zero times. Pair this with the 422 above to prove ordering. |
| Another tenant cannot read the row | A creates and then gets the row. B uses its own valid token and tenant header to get A’s ID, then a missing ID. | A gets 200 and its own row. Both B reads return 404 with equivalent public errors, allowing for distinct trace IDs. This checks row visibility after successful authentication and membership resolution. |
| A patch preserves omitted fields | A creates with nonempty links, changes only the name and reads again. | Both the typed PATCH response and subsequent Get contain the new name and original links. The wire body contains only the name, and the raw response omits the hidden field. |
| Another tenant cannot update the row | B’s editor patches A’s ID, a missing ID and B’s own ID. | The foreign and missing requests both give 404. B’s own update succeeds, and A’s stored values survive. |
| Delete is tenant-scoped | A’s editor and B’s administrator attempt to delete A’s row. A’s administrator then deletes it. | The editor gets 403, B gets the same 404 as for a missing ID, and the row survives both attempts. A receives exactly `{ code: 200 }` and the next Get and Delete both return 404. |
| List rows and counts are tenant-scoped | Create A1, B1 and A2. A’s viewer requests two one-row pages and a page past the end. B’s viewer and a viewer in an empty tenant each request the default page. | A sees its two distinct rows and a count of 2 on every page, including the empty page. B sees only B1 and a count of 1. The empty tenant gets 200 with an empty list and a count of 0. |
| Filtered pages preserve sort priority | A creates two same-name services with known creation times and one product. B also creates a service. After checking one-row pages, A creates an older service with an earlier name. | A’s filtered pages show newer then older with count 2. B gets its service with count 1. The third service sorts first by name and last when creation time has priority. |

Use real fetch for these tests. An observing fetch can forward the request and clone the response before the client decodes it. This catches a server leak that client-side projection could hide. For intentionally invalid input, a test wrapper can replace the body *after* the client encodes a valid request and forward it to the real listener, or the transport test can send raw JSON directly. Count actual requests and handler invocations. Keep test-only observation in the harness and use independent expected status, field and value assertions.
